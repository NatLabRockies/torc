 Plan: Run Jobs Through srun (Issue #169)                                                                                                         │
│                                                                                                                                                  │
│ Context                                                                                                                                          │
│                                                                                                                                                  │
│ When torc runs inside a Slurm allocation, individual job subprocesses are spawned as plain bash                                                  │
│ subprocesses with no cgroup enforcement. The HPC team wants jobs wrapped with srun so:                                                           │
│                                                                                                                                                  │
│ 1. Slurm creates a cgroup for each job, enforcing CPU/memory limits from the job's resource                                                      │
│ requirements.                                                                                                                                    │
│ 2. sstat can collect additional per-step metrics.                                                                                                │
│ 3. Slurm management has visibility into what jobs are actually running (not just the torc runner).                                               │
│                                                                                                                                                  │
│ User preferences: auto-detect via SLURM_JOB_ID env var; add limit_resources config option                                                        │
│ (default true) so users can opt out of cgroup enforcement without disabling srun.                                                                │
│                                                                                                                                                  │
│ ---                                                                                                                                              │
│ Approach                                                                                                                                         │
│                                                                                                                                                  │
│ 1. Add limit_resources to ClientSlurmConfig                                                                                                      │
│                                                                                                                                                  │
│ File: src/config/client.rs                                                                                                                       │
│                                                                                                                                                  │
│ Add field to ClientSlurmConfig:                                                                                                                  │
│                                                                                                                                                  │
│ /// When true (default), srun passes --mem and --cpus-per-task to enforce cgroup limits.                                                         │
│ /// Set to false to allow jobs to exceed their stated resource requirements.                                                                     │
│ pub limit_resources: bool,                                                                                                                       │
│                                                                                                                                                  │
│ Default: true. Update Default impl accordingly.                                                                                                  │
│                                                                                                                                                  │
│ 2. Build the srun command in AsyncCliCommand::start()                                                                                            │
│                                                                                                                                                  │
│ File: src/client/async_cli_command.rs                                                                                                            │
│                                                                                                                                                  │
│ start() currently builds the command as:                                                                                                         │
│                                                                                                                                                  │
│ let mut cmd = crate::client::utils::shell_command();  // bash -c                                                                                 │
│ let command_str = if let Some(ref invocation_script) = self.job.invocation_script {                                                              │
│     format!("{} {}", invocation_script, self.job.command)                                                                                        │
│ } else {                                                                                                                                         │
│     self.job.command.clone()                                                                                                                     │
│ };                                                                                                                                               │
│ cmd.arg(&command_str)...spawn()                                                                                                                  │
│                                                                                                                                                  │
│ Change: when SLURM_JOB_ID is present, replace the shell wrapper with an srun invocation                                                          │
│ that runs the job command directly (srun manages the shell):                                                                                     │
│                                                                                                                                                  │
│ if std::env::var("SLURM_JOB_ID").is_ok() {                                                                                                       │
│     // Running inside a Slurm allocation — use srun for cgroup enforcement                                                                       │
│     let mut cmd = Command::new("srun");                                                                                                          │
│     cmd.arg("--exclusive");  // each step gets its own cgroup                                                                                    │
│     if let Some(rr) = resource_requirements {                                                                                                    │
│         if limit_resources {                                                                                                                     │
│             cmd.arg(format!("--cpus-per-task={}", rr.num_cpus));                                                                                 │
│             let mem_mb = memory_string_to_mb(&rr.memory);                                                                                        │
│             cmd.arg(format!("--mem={}M", mem_mb));                                                                                               │
│         }                                                                                                                                        │
│     }                                                                                                                                            │
│     // Run via shell so job.command can use shell features                                                                                       │
│     cmd.args(["bash", "-c", &command_str]);                                                                                                      │
│     cmd...spawn()                                                                                                                                │
│ } else {                                                                                                                                         │
│     // Local execution — current behavior unchanged                                                                                              │
│     let mut cmd = crate::client::utils::shell_command();                                                                                         │
│     cmd.arg(&command_str)...spawn()                                                                                                              │
│ }                                                                                                                                                │

  ---
  Question 2 first: sstat for resource monitoring

  Short answer: the existing polling is sufficient; sstat isn't worth it.

  Here's why:

  Current monitoring (sysinfo): The ResourceMonitor spawns a background thread that polls /proc/<pid>/... recursively for the srun process and all
  its children. On a single-node job — the normal torc use case — this captures the full resource picture accurately and at configurable granularity
   (e.g., every 5 seconds).

  What sstat adds:
  - sstat queries the slurmstepd daemon on the compute node via Slurm's RPC mechanism — NOT the central slurmctld. So your concern about hitting the
   Slurm server is valid but the right way: it's the compute node that receives the message.
  - For a workflow running 20 concurrent jobs, polling every 5–10 seconds would send 2–4 RPC messages/second to slurmstepd daemons. That's noisy
  without much benefit.
  - sstat only works on running steps; once the step exits, you need sacct (which does query the central slurmdbd).
  - The MaxRSS reported by sstat/sacct reads from the same kernel cgroup accounting that sysinfo reads from /proc — the numbers would agree for
  single-node jobs.

  One genuinely useful case: multi-node srun steps (num_nodes > 1). Torc can only see the local process tree; sstat aggregates across all nodes. But
   torc's workflow model currently doesn't support multi-node per-job steps, so this is moot for now.

  Verdict: Don't add sstat polling. If Slurm-native metrics ever become desirable (e.g., for multi-node jobs), calling sacct once per job at
  completion — not periodically — would be the right approach. The single-query cost is negligible and sacct's accounting data is final.

❯ Suppose I wanted to use sstat because of the information it provides, would it involve a request to the Slurm server?

⏺ No — sstat does not contact slurmctld (the central Slurm scheduling server). Here's the precise call path:

  sstat → slurmstepd (on the compute node running the step)

  sstat retrieves live accounting data directly from the slurmstepd daemon that manages each job step. slurmstepd runs as a child of slurmd on the
  same node where the step was launched, and it maintains real-time cgroup/proc metrics locally. The RPC goes node-to-node (or loopback if the
  caller is on the same node), never touching the central controller.

  Compare this to sacct, which queries slurmdbd — the Slurm accounting database daemon — which IS a central service shared across the cluster.

  For torc's specific case this is favorable: when the torc job runner is inside a Slurm allocation, srun steps land on the same node(s). An sstat
  call from the runner to a co-located step is a loopback RPC to a process on the same machine — essentially zero network cost.

  There is one caveat: to locate a step (map jobid.stepid → which node), sstat may make a brief lookup against slurmctld. This lookup is lightweight
   and cached, but it does exist. If torc already knows the node (it started the step via srun --exclusive), you could potentially avoid even that
  by querying slurmstepd directly — but that's not worth the complexity; the slurmctld lookup for a single step is negligible.

  Practical implication: if you wanted to call sstat once per job at completion time (not periodically) to capture Slurm-measured MaxRSS, CPU time,
  and disk I/O as a complement to the sysinfo metrics, the server-side cost would be one lightweight slurmctld lookup per job — comfortably within
  what any Slurm cluster handles. The concern would shift from "server load" to "is sstat available before the step is cleaned up?" — which it is,
  as long as you call it before wait() returns on the srun process.

  ---
  Periodic sstat polling and Slurm load

  Yes, it would add load, but the more fundamental problem is redundancy. The existing ResourceMonitor already polls /proc via sysinfo at
  configurable intervals and captures peak/average memory and CPU. sstat reads the same kernel cgroup/proc accounting that sysinfo reads — so for a
  single-node step the numbers would agree.

  The unique information sstat/sacct provides that sysinfo does not:
  - MaxDiskRead / MaxDiskWrite — I/O bytes, which sysinfo doesn't track
  - MaxVMSize — virtual memory peak
  - Multi-node aggregation (sysinfo only sees the local process tree)

  Periodic sstat polling for those three fields would cost: N jobs × (1 slurmctld step-location RPC + 1 slurmstepd RPC) per poll interval. At 20
  jobs / 30-second interval that's ~0.7 RPC-pairs/second — survivable but noisy for what amounts to disk I/O stats. Getting sstat/sacct data once at
   completion is cleaner and sufficient.

  ---
  Multi-node srun — critical bug in the current implementation

  The current code emits:

  srun --exclusive --cpus-per-task=N --mem=XM bash -c "cmd"

  This is wrong for multi-node allocations. Without --nodes=1 --ntasks=1, srun defaults to spanning all nodes available to the calling process. In a
   4-node allocation, this would run cmd simultaneously on all 4 nodes — like a miniature mpirun. That's not what torc wants for a single per-job
  command.

  start_one_worker_per_node = false (one runner on head node)

  The runner holds all N nodes. Every srun call without --nodes=1 would fan out across all nodes. Concretely: if two jobs are running
  simultaneously, their srun steps compete for the same 4-node pool, and each step tries to span all nodes. This causes step serialization or
  outright failures depending on --exclusive interactions.

  Fix needed: add --nodes=1 --ntasks=1 to pin each step to a single node.

  start_one_worker_per_node = true (one runner per node)

  Each runner has SLURM_JOB_ID set (it was launched via srun or sbatch --exclusive), but its available node set is effectively its own node only
  (since --exclusive was used to launch it). An srun from that runner would run on the node the runner is on — which is actually the correct
  behavior. This case is safer, but adding --nodes=1 --ntasks=1 is still the right defensive posture.

  Additionally, with per-node runners, you probably want --nodelist=$SLURMD_NODENAME to ensure the step runs on the runner's own node rather than
  Slurm picking any available node in the allocation.
